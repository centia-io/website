# Snapshots

A **snapshot** is a point-in-time export of a table, view or materialized view to a cloud-native file — **GeoParquet** by default, optionally also **FlatGeobuf**. Snapshots are taken asynchronously by a background worker, stored in object storage (or on local disk when self-hosting) and served back through the API with `HEAD` and HTTP byte-range support — so analytical tools like DuckDB can read them straight from Centia without downloading the whole file, and without any storage credentials.

Snapshots never touch the operational PostGIS data. They give you an **immutable, dated history** of a relation that you can query, diff, archive or hand to a partner.

## Formats

Snapshots can be produced in one or more formats. The default is Parquet; the server is extensible, and today two formats are available:

| Format id | File | Media type | Needs geometry | Best for |
|---|---|---|---|---|
| `parquet` | `data-{id}.parquet` | `application/vnd.apache.parquet` | No (plain Parquet for non-spatial relations) | Analytics: DuckDB, pandas/Arrow, Spark, Athena |
| `flatgeobuf` | `data-{id}.fgb` | `application/flatgeobuf` | Yes | Web maps and streaming features by bounding box |

### What is (Geo)Parquet?

[Apache Parquet](https://parquet.apache.org/) is a **columnar, compressed, self-describing** file format for tabular data. Instead of storing one row after another (as CSV or GeoJSON do), a Parquet file stores each column together, split into **row groups**, with a **footer** that holds the schema and per-column statistics (min/max, null counts) for every row group.

That layout has two consequences that matter for geodata:

- **Columnar compression** — values of the same column compress extremely well, so a Parquet file is typically a fraction of the size of the same data as GeoJSON or CSV.
- **Selective reads** — a reader first fetches the footer, then only the columns and row groups it actually needs. Over HTTP this is done with **range requests**, which is why the snapshot endpoints support them: a `SELECT count(*)` or a query filtered on an indexed column reads a few kilobytes of a multi-gigabyte file.

[GeoParquet](https://geoparquet.org/) is Parquet with a standardised `geo` metadata block describing the geometry column (WKB encoding, CRS, bounding box). It is understood by GDAL/OGR, DuckDB (`spatial` extension), GeoPandas, R (`sfarrow`), QGIS, Apache Spark, Amazon Athena and most other modern data tools.

### What is FlatGeobuf?

[FlatGeobuf](https://flatgeobuf.org/) is a **single-file, binary vector format** built on FlatBuffers, with a **packed spatial index** at the front of the file. A reader that wants the features inside a bounding box fetches the index with a range request and then only the byte ranges of the matching features — so a web map can stream just the visible part of a large layer straight from the snapshot URL. It carries one layer (named after the relation), is read by GDAL/OGR and QGIS, by Leaflet, OpenLayers and MapLibre through the [flatgeobuf](https://github.com/flatgeobuf/flatgeobuf) JavaScript library, and by DuckDB's `spatial` extension through `ST_Read`. Unlike Parquet it is row-oriented and uncompressed, so it is the wrong tool for column scans and aggregations.

### Choosing a format

- **Parquet** when the consumer is an analytical engine — DuckDB, pandas/pyarrow, Spark — or when the relation has no geometry. Columnar reads and compression make it the smaller and faster file for queries, joins and change detection.
- **FlatGeobuf** when the consumer is a map: a browser client that streams features by bbox, or a desktop GIS that wants a single spatial file with an index.
- **Both** when a dataset is delivered to analysts and to map clients alike; the two files sit side by side in the same snapshot and are downloaded separately.

## Why snapshots?

- **History without copies in the database** — one file per relation per day, versioned by date, without adding tables or load to PostGIS.
- **Small files** — columnar compression makes them cheap to store and fast to transfer.
- **Query in place** — analysts read footers and row groups over HTTP; nothing has to be downloaded or imported first.
- **Works everywhere** — DuckDB, Python (pyarrow/GeoPandas), R, QGIS, Spark and cloud query engines all read GeoParquet natively.
- **Change detection** — every snapshot carries a row count and a `schema_version` fingerprint of the column list, so schema drift and data changes are easy to detect and analyses are reproducible.
- **Same access model** — reads are authenticated with the usual bearer token and follow [privileges](./privileges.mdx) and [geofence rules](./rules.mdx). Users never see S3 credentials.

Typical use cases:

- Point-in-time analyses and audits — *"how did the dataset look on date X?"*
- Change detection between two dates.
- Offloading heavy analytics from the operational database to DuckDB or Spark.
- Delivering data to partners as files rather than database access.
- Feature pipelines for machine learning.
- Long-term archiving in inexpensive object storage.

## Taking a snapshot

Snapshots are queued by the **super-user** with the job API. `POST` returns `202 Accepted` immediately; a worker picks the job up within about a minute, exports the relation with `ogr2ogr` and publishes the files.

```http title="Request"
POST https://api.centia.io/api/v4/snapshots HTTP/1.1
Content-Type: application/json
Authorization: Bearer abc123

{
    "schema": "geodanmark",
    "relation": "bygning",
    "srs": 25832
}
```

- **`schema`** and **`relation`** — required. The relation may be a table, a view or a materialized view. Names must match `^[A-Za-z0-9_-]+$`.
- **`srs`** — optional EPSG code to reproject to. Omit it to keep the relation's native SRID.
- **`formats`** — optional array of [format ids](#formats), e.g. `["parquet", "flatgeobuf"]`, produced in that order. Omit it to use the server default (`["parquet"]` unless configured otherwise; scheduled imports with `snapshot: true` use the same default). Unknown ids, duplicates and an empty array are `400`. A format that needs a geometry column is **skipped** with a reason when the relation has none, and the snapshot fails only if nothing at all could be produced; requesting *only* geometry formats for a non-spatial relation is refused up front with `400`.

The body may also be an **array** of request objects to queue several relations at once. Every relation is checked before anything is queued, so one bad element (unknown relation, a job already active, a relation listed twice, or an empty list) queues nothing — and the `202` body is then an array in request order.

```json title="Response 202"
{
    "id": "0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b",
    "status": "pending",
    "_links": {
        "self": "/api/v4/snapshots/0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b"
    }
}
```

```http title="Request — several relations"
POST https://api.centia.io/api/v4/snapshots HTTP/1.1
Content-Type: application/json
Authorization: Bearer abc123

[
    { "schema": "geodanmark", "relation": "bygning" },
    { "schema": "geodanmark", "relation": "vejmidte", "srs": 25832 }
]
```

```json title="Response 202"
[
    { "id": "0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b", "status": "pending", "_links": { "self": "/api/v4/snapshots/0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b" } },
    { "id": "c2a7e9d4-1b3f-4e5a-8c6d-0f1e2d3c4b5a", "status": "pending", "_links": { "self": "/api/v4/snapshots/c2a7e9d4-1b3f-4e5a-8c6d-0f1e2d3c4b5a" } }
]
```

Only one job per relation can be active at a time — a second `POST` while one is `pending` or `running` is answered with `409` (`SNAPSHOT_IN_PROGRESS`). Snapshots are keyed by relation and **UTC date**: running a second snapshot of the same relation on the same day publishes the new one and marks the earlier one `superseded`, so readers always see at most one snapshot per day.

### Polling the job

Follow `_links.self` until `status` is `succeeded` or `failed`. A comma-separated list of ids returns an array of jobs; if any id is unknown the response is `404`:

```http title="Request"
GET https://api.centia.io/api/v4/snapshots/0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b HTTP/1.1
Authorization: Bearer abc123
```

```json title="Response"
{
    "id": "0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b",
    "schema": "geodanmark",
    "relation": "bygning",
    "srs": 25832,
    "status": "succeeded",
    "snapshot_date": "2026-09-16",
    "s3_path": "s3://gc2-parquet/prod/mydb/schema=geodanmark/relation=bygning/_gc2_snapshot_date=2026-09-16/",
    "row_count": 123456,
    "schema_version": "9e107d9d372bb6826bd81d3542a419d6",
    "relation_schema": [
        { "column_name": "gid", "data_type": "integer" },
        { "column_name": "the_geom", "data_type": "geometry(Point,25832)" }
    ],
    "formats": [
        { "format": "parquet", "status": "produced", "file": "data-0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b.parquet", "size_bytes": 8421376, "media_type": "application/vnd.apache.parquet" },
        { "format": "flatgeobuf", "status": "produced", "file": "data-0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b.fgb", "size_bytes": 19873402, "media_type": "application/flatgeobuf" }
    ],
    "error": null,
    "username": "mydb",
    "created": "2026-09-16T10:00:00+00:00",
    "started": "2026-09-16T10:00:31+00:00",
    "finished": "2026-09-16T10:02:10+00:00"
}
```

| Status | Meaning |
|---|---|
| `pending` | Queued, not yet picked up by the worker. |
| `running` | Export in progress. |
| `succeeded` | Published and readable through the read API under `snapshot_date`. |
| `failed` | The export failed; `error` holds the reason (for example the relation was dropped, or `ogr2ogr` reported an error). There are no automatic retries — `POST` again. |
| `superseded` | Replaced by a later snapshot of the same relation on the same date. |

`snapshot_date`, `s3_path`, `row_count`, `schema_version`, `relation_schema`, `started` and `finished` are `null` until set. `formats` lists every requested format and its outcome: `requested` while the job is queued, then `produced` (with `file`, `size_bytes` and `media_type`) or `skipped` (with a `reason`, e.g. `relation has no geometry column`). `schema_version` is an MD5 fingerprint of the column names and types at snapshot time — compare it across snapshots to detect schema changes.

`GET /api/v4/snapshots` lists the 50 newest jobs, newest first, with optional `?schema=` and `?relation=` filters:

```http title="Request"
GET https://api.centia.io/api/v4/snapshots?schema=geodanmark&relation=bygning HTTP/1.1
Authorization: Bearer abc123
```

| Status | Meaning |
|---|---|
| `400` | `INVALID_REQUEST` — missing or malformed `schema`/`relation`, a non-integer `srs`, an unknown, duplicate or empty `formats` list, only geometry formats for a non-spatial relation, a relation listed twice, or an empty list. |
| `403` | The caller is not the super-user. |
| `404` | `RELATION_NOT_FOUND` on `POST`; `NO_SNAPSHOT_ERROR` on `GET` with an unknown id. |
| `409` | `SNAPSHOT_IN_PROGRESS` — a job for the relation is already pending or running. |
| `501` | `SNAPSHOT_NOT_CONFIGURED` — the server has no snapshot storage configured. |

## What gets stored

Each snapshot is a directory under a **Hive-style partitioned** path, so query engines that understand `key=value` path segments (DuckDB, Spark, Athena) can scan a whole relation history at once and filter by date. It holds one data file per produced format plus a metadata file:

```
{prefix}/{database}/schema={schema}/relation={relation}/_gc2_snapshot_date=2026-09-16/
    data-{snapshot_id}.parquet
    data-{snapshot_id}.fgb          (when flatgeobuf was requested)
    metadata-{snapshot_id}.json
    item.json                        (STAC Item, see below)
```

The date segment is prefixed with `_gc2_` so the partition column a Hive reader derives from it can never collide with a column of your data. File names carry the snapshot id, so a re-run on the same day never overwrites a file someone may be reading.

`metadata-{snapshot_id}.json` describes the export:

```json title="metadata-{snapshot_id}.json"
{
    "snapshot_id": "0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b",
    "snapshot_date": "2026-09-16",
    "created_at": "2026-09-16T10:02:10Z",
    "database": "mydb",
    "source": "geodanmark.bygning",
    "row_count": 123456,
    "schema_version": "9e107d9d372bb6826bd81d3542a419d6",
    "schema": [
        { "column_name": "gid", "data_type": "integer" },
        { "column_name": "the_geom", "data_type": "geometry(Point,25832)" }
    ],
    "crs": "EPSG:25832",
    "bbox": [8.07, 54.56, 15.19, 57.75],
    "formats": [
        { "format": "parquet", "status": "produced", "file": "data-0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b.parquet", "size_bytes": 8421376, "media_type": "application/vnd.apache.parquet" },
        { "format": "flatgeobuf", "status": "produced", "file": "data-0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b.fgb", "size_bytes": 19873402, "media_type": "application/flatgeobuf" }
    ],
    "files": [
        { "name": "data-0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b.parquet", "size_bytes": 8421376 },
        { "name": "data-0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b.fgb", "size_bytes": 19873402 }
    ]
}
```

`bbox` is the relation's extent in WGS84 (`[minx, miny, maxx, maxy]`), or `null` for a non-spatial or empty relation.

### STAC catalog

Every publish also rewrites a static **[STAC](https://stacspec.org/) 1.1.0 catalog** of the whole database next to the data, so the store itself is browsable with STAC Browser, pystac or the QGIS STAC plugin — no API involved:

```
{prefix}/{database}/catalog.json                                            Catalog, id = database
{prefix}/{database}/schema={schema}/relation={relation}/collection.json     Collection, id = schema.relation
{prefix}/{database}/schema={schema}/relation={relation}/_gc2_snapshot_date=2026-09-16/item.json   Item, id = schema.relation/2026-09-16
```

- The **catalog** links one child collection per relation with at least one published snapshot.
- Each **collection** carries the layer's title, abstract and tags from its [metadata](./metadata.mdx), a spatial extent that is the union of its snapshots' footprints, a temporal extent from oldest to newest snapshot date, and summaries of `schema_version` and CRS.
- Each **item** has the snapshot's bbox as a WGS84 polygon, `datetime` at the snapshot date, `gc2:row_count`, `gc2:snapshot_id`, `gc2:schema_version`, the CRS as `proj:code`, and one **asset per produced format** — `data` for the Parquet, `flatgeobuf` for the FlatGeobuf — plus a `metadata` asset for the JSON file.

All links are relative to the document that carries them, so the catalog works unchanged on S3 and on local disk. The catalog is written to the storage, not served by the API; it is meant for consumers with direct access to the bucket or directory. The rebuild is best effort: a snapshot counts as succeeded even if the catalog could not be rewritten.

## Reading snapshots

Published snapshots are read per relation. Any user with a bearer token and read access to the relation can use these endpoints (see [Access](#access)); anonymous access is not supported.

```
https://api.centia.io/api/v4/schemas/{schema}/relations/{relation}/snapshots
```

| Method | Route | Returns |
|---|---|---|
| `GET` | `/snapshots` | Array of published snapshots, newest first |
| `GET` | `/snapshots/{date}` | One snapshot with full metadata and links |
| `GET` `HEAD` | `/snapshots/{date}/data` | The primary data file — the Parquet when produced, else the only produced file — with byte-range support |
| `GET` `HEAD` | `/snapshots/{date}/data/{format}` | The data file in one named format (`/data/parquet`, `/data/flatgeobuf`), same semantics as `/data` |
| `GET` `HEAD` | `/snapshots/{date}/files/{name}` | Any file of the snapshot by name, including `metadata-{id}.json` |

```json title="Response"
{
    "snapshot_date": "2026-09-16",
    "snapshot_id": "0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b",
    "row_count": 123456,
    "size_bytes": 8421376,
    "schema_version": "9e107d9d372bb6826bd81d3542a419d6",
    "files": [ "..." ],
    "formats": [ "..." ],
    "published": "2026-09-16T10:02:10+00:00",
    "srs": 25832,
```

The date must be a valid `YYYY-MM-DD` or `latest`; an unknown date is `404` (`NO_SNAPSHOT_ERROR`). `_links.data` is present only when the snapshot has a Parquet file; the per-format download links are always in `formats[].href`.

### Latest snapshot

Use `latest` in place of a date to keep a **fixed URL to the newest published snapshot** of a relation: `/snapshots/latest` (metadata), `/snapshots/latest/data`, `/snapshots/latest/data/{format}` and `/snapshots/latest/files/{name}` all resolve to the newest snapshot at request time. The metadata still reports the real `snapshot_date`, and dated responses carry a `_links.latest` link. These responses are sent with `Cache-Control: no-cache`, so clients revalidate after every publish; `404` (`NO_SNAPSHOT_ERROR`) means nothing is published yet.

```http title="Request"
GET https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/latest HTTP/1.1
Authorization: Bearer abc123
```

In the data store the partition layout is unchanged; each relation additionally gets a small `latest.json` pointer (snapshot date, id, item and asset paths) next to its STAC collection, and the collection carries a `latest-version` link to the newest item.

### Download the data

`/snapshots/{date}/data` serves the primary data file: the Parquet when one was produced, otherwise the only produced file. `/snapshots/{date}/data/{format}` serves the file in a named format — `/data/flatgeobuf` for the FlatGeobuf — with its own media type (`application/flatgeobuf`); an unknown format id is `400` and a format the snapshot did not produce (skipped or never requested) is `404`. Both `HEAD` and `GET` return `Accept-Ranges: bytes`, `Content-Length`, an `ETag` equal to the snapshot id and `Last-Modified` from the publish time, so Parquet readers can size the file and fetch the footer and individual row groups with `Range` requests:

```http title="Request — the last 64 KiB (where the footer lives)"
GET https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data HTTP/1.1
Authorization: Bearer abc123
Range: bytes=-65536
```

```http title="Response"
HTTP/1.1 206 Partial Content
Content-Type: application/vnd.apache.parquet
Content-Range: bytes 8355840-8421375/8421376
Content-Length: 65536
Accept-Ranges: bytes
ETag: "0f4c1b2e-4d1a-4c3f-9a0b-7b1d2e3f4a5b"
```

A single range (`bytes=a-b`, `bytes=a-` or `bytes=-n`) is honoured with `206`; a range that starts beyond the end of the file is `416` with `Content-Range: bytes */{size}`. A header naming several ranges is ignored and the whole file is returned with `200`.

`/snapshots/{date}/files/{name}` serves any file listed in the snapshot's `files`, plus `metadata-{snapshot_id}.json`, with the same `HEAD`/`Range` semantics. When a snapshot has several data files and none of them is Parquet, the bare `/data` is ambiguous and answers `409` (`MULTI_FILE_SNAPSHOT`) with the `/data/{format}` paths in the message.

:::note Proxy or redirect
By default the file is **streamed through the API** (proxy mode). A self-hosted server can be configured for **redirect mode** instead, where `/data`, `/data/{format}` and `/files/{name}` answer `302` with a short-lived presigned storage URL after the same authorization check, so large downloads bypass the API server. Clients should follow redirects and repeat their `Range` header against the redirected URL.
:::

## Access

Reads are authorized before any file name or storage location is resolved:

- The **super-user** can always read.
- A **sub-user** can read snapshots of relations in schemas they own, and of relations where they hold `read` or `write` [privilege](./privileges.mdx).
- A sub-user with a `deny` or `limit` [geofence rule](./rules.mdx) on the relation is refused with `403` (`GEOFENCE_RULES_APPLY`): a snapshot is the whole relation in one file and cannot honour a row filter. An `allow` rule does not block the read.
- Anonymous requests are not accepted.

| Status | Meaning |
|---|---|
| `400` | `INVALID_REQUEST` — malformed schema, relation, date or file name, or an unknown format id. |
| `403` | `INSUFFICIENT_PRIVILEGES` or `GEOFENCE_RULES_APPLY`. |
| `404` | `NO_SNAPSHOT_ERROR` — no published snapshot for that date, no such file, or the snapshot did not produce that format. |
| `409` | `MULTI_FILE_SNAPSHOT` — several data files and no Parquet; use `/data/{format}`. |
| `416` | Range not satisfiable. |
| `501` | `SNAPSHOT_NOT_CONFIGURED` — no snapshot storage on this server. |
| `502` | `SNAPSHOT_STORAGE_ERROR` — the storage backend failed. |

## Querying snapshots

### DuckDB

DuckDB's `httpfs` extension reads Parquet over HTTP with range requests, and an `http` secret carries the bearer token. Row counts and filtered queries touch only the footer and the row groups they need:

```sql title="DuckDB"
INSTALL httpfs; LOAD httpfs;
INSTALL spatial; LOAD spatial;

CREATE SECRET centia (TYPE http, BEARER_TOKEN 'abc123');

-- Count rows without downloading the file
SELECT count(*)
FROM read_parquet('https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data');

-- Query attributes and geometry
SELECT gid, ST_Area(the_geom) AS area
FROM read_parquet('https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data')
WHERE kommunekode = '0101';
```

A dashboard or notebook that should always see the current data reads the `latest` alias instead of a date:

```sql title="Always the newest snapshot"
SELECT count(*)
FROM read_parquet('https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/latest/data');
```

Combine several dates to compare them — `union_by_name` keeps this working when columns were added between snapshots:

```sql title="Rows that exist today but not yesterday"
WITH today AS (
    SELECT * FROM read_parquet('https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data')
), yesterday AS (
    SELECT * FROM read_parquet('https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-15/data')
)
SELECT count(*) FROM today WHERE gid NOT IN (SELECT gid FROM yesterday);
```

```sql title="Several snapshots as one table"
SELECT *
FROM read_parquet([
    'https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-15/data',
    'https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data'
], union_by_name = true);
```

Before joining two snapshots, compare their `schema_version` from the list endpoint: a different fingerprint means the column set or types changed in between.

### FlatGeobuf in a web map

The [flatgeobuf](https://github.com/flatgeobuf/flatgeobuf) JavaScript library streams only the features inside a bounding box, using range requests against the snapshot URL. Because the endpoint requires a bearer token, pass it with the `headers` option; here with Leaflet:

```js title="Leaflet — stream the features in the current view"
import { geojson } from 'flatgeobuf';

const url = 'https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data/flatgeobuf';
const headers = { Authorization: 'Bearer abc123' };

async function loadView() {
    const b = map.getBounds();
    const rect = { minX: b.getWest(), minY: b.getSouth(), maxX: b.getEast(), maxY: b.getNorth() };
    const layer = L.geoJSON().addTo(map);
    for await (const feature of geojson.deserialize(url, { rect, headers })) {
        layer.addData(feature);
    }
}
map.on('moveend', loadView);
```

DuckDB's `spatial` extension reads the same file with `ST_Read`, which is convenient when a FlatGeobuf is the only format produced:

```sql title="DuckDB"
INSTALL spatial; LOAD spatial;
SELECT count(*) FROM ST_Read('https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data/flatgeobuf');
```

### GDAL/OGR and QGIS

GDAL (3.5 or later, built with the Parquet driver) reads the file over HTTP through `/vsicurl/` when the bearer token is passed as a header, and any GDAL-based desktop tool — including QGIS — opens a downloaded snapshot as a normal vector layer:

```bash title="ogrinfo over HTTP"
GDAL_HTTP_HEADERS="Authorization: Bearer abc123" \
ogrinfo -so -al "/vsicurl/https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data"
```

```bash title="Convert a snapshot to GeoPackage"
GDAL_HTTP_HEADERS="Authorization: Bearer abc123" \
ogr2ogr bygning-2026-09-16.gpkg "/vsicurl/https://api.centia.io/api/v4/schemas/geodanmark/relations/bygning/snapshots/2026-09-16/data"
```

The FlatGeobuf works the same way through `/data/flatgeobuf`; its spatial index lets `ogrinfo -spat` and QGIS fetch only the features in a bounding box.

## Snapshots after scheduled imports

A [scheduler](./scheduler.mdx) job can queue a snapshot automatically after each successful import by setting the job's `"snapshot": true` through the Scheduler API. The flag is API-only for now — the admin UI has no field for it yet.

## Self-hosting

Snapshots are available on Centia Cloud out of the box. On a self-hosted [open source](./opensource.mdx) installation the feature is off until storage is configured:

- **Configuration** — the `snapshot` block in `App.php`: `storage` is `s3` (with `bucket`, `prefix`, `region`; credentials from the `s3` block) or `local` (with `localPath`); `download` is `proxy` (default) or `redirect`, `urlTtl` sets the presigned URL lifetime in seconds (default 300), and `formats` is the list of formats produced when a request names none (default `["parquet"]`). Without a configured storage the API answers `501` (`SNAPSHOT_NOT_CONFIGURED`).
- **Worker** — the export runs from `app/scripts/snapshot_worker.php`, scheduled by cron every minute under `flock` (the official Docker image ships the crontab line). It needs `ogr2ogr` with the Parquet driver (GDAL 3.5 or later); the FlatGeobuf driver ships with GDAL 3.1 or later.
- **Apache** — the vhost must set `SetEnv ap_trust_cgilike_cl 1`; without it, `mod_proxy_fcgi` on Apache 2.4.6x strips the backend's `Content-Length`, which makes `HEAD` answer without a length and `GET` chunked, and breaks Parquet readers. The official image includes it.
